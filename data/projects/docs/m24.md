# Raft (MIT 6.5840 labs)

**Goal.** A Raft implementation in Go that passes every test of MIT 6.5840 lab 3 (leader election, log replication, persistence and snapshots) 100 times in a row, and a public write-up of the bugs that took longest to find.

**Why.** Software Architect roadmap: `software-architect/distributed-systems` and `software-architect/go`. Skills: consensus, Go concurrency, and debugging distributed systems, where the bug appears in one run out of fifty and the log is the only witness. The sharded key-value store of project 38 runs on this Raft, so every latent bug here resurfaces there.

**Scope.** MVP: parts 3A to 3D in the course's framework, a test loop that runs each part hundreds of times in parallel, structured logging you can filter by server and term, and the bug write-up. Stretch: a log visualiser that colours output by server and topic; pre-vote; a latency and throughput measurement of agreement under the lab's simulated network. The course asks that solutions stay private, so the repository with code is private and only the write-up is public.

**Architecture.** Each peer runs a few long-lived goroutines around one mutex-protected state struct: an election ticker, a heartbeat and replication loop per follower, and an applier that sends committed entries to the service on the apply channel. RPC handlers (RequestVote, AppendEntries, InstallSnapshot) update the same state. Persistent state (term, vote, log, snapshot) is saved before any RPC reply that depends on it.

```
ticker ─▶ election ─▶ RequestVote ─▶ peers
leader ─▶ replicators ─▶ AppendEntries / InstallSnapshot ─▶ peers
                │
          commitIndex ─▶ applier ─▶ applyCh ─▶ service
                │
            persister (term, vote, log, snapshot)
```

**Stack.** Go, the 6.5840 lab skeleton and its labrpc simulated network, the race detector, a shell or Python script for parallel test runs, and a small log-pretty-printer.

**Milestones.** Read the paper's Figure 2 and set up logging and the test loop (4 h) · 3A leader election (8 h) · 3B log replication (12 h) · 3C persistence and fast log backtracking (6 h) · 3D snapshots and log compaction (6 h) · 100-run validation and the bug write-up (4 h). Total 40 h.

**Done when.** Every lab 3 test passes 100 consecutive times with the race detector on, run by the parallel test script that ships in the private repository. Each part stays inside the real-time and CPU-time limits the lab handout gives. The public write-up describes at least five bugs: the symptom, how the logs revealed it, the fix, and which rule of Figure 2 it broke.

**Measure and report.** Failures per 1,000 runs per part before and after each fix; mean time to elect a leader after the old one is partitioned; RPC count per agreement in the figure-8 and unreliable tests; total test-suite wall time.

**Pitfalls.** Holding the mutex across an RPC call or a channel send, which deadlocks under the unreliable network. Resetting the election timer on every RPC instead of only on valid ones. Committing entries from an earlier term by counting replicas (the figure-8 case). Persisting state after replying instead of before. Off-by-one log indices once a snapshot shifts the start of the log.

**References.** paper-raft, mit-6-5840, kleppmann-distributed-systems, ddia, tour-of-go.

**Write-up.** The public bug write-up as a post: one section per bug with the log excerpt that exposed it, a timeline diagram of the trickiest failure, the failure-rate table, and what you would change about the code's structure before building the key-value store on it.
