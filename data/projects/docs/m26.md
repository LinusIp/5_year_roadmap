# URL shortener, then scale it: load test, cache, queue, shard, autoscale on Kubernetes

**Goal.** A URL shortener taken from the simplest working version to a sharded, cached, autoscaled deployment on Kubernetes, with a load test and a before-and-after number at every step, written up as a case study.

**Why.** Software Architect roadmap: `software-architect/distributed-systems`, `software-architect/messaging-queues`, `software-architect/sql-databases`, `software-architect/containers` and `software-architect/cloud-design-patterns`. Skills: load testing, caching, Kubernetes and capacity planning. The method matters more than the service: measure, find the bottleneck, change one thing, measure again. The same loop runs the inference router and the capstone deployment.

**Scope.** MVP: create and redirect endpoints with collision-free short codes, Postgres storage, a k6 load test with a read-heavy, Zipf-distributed key mix, then a Redis read-through cache, asynchronous click counting through a queue, storage sharded by key hash, and a Kubernetes deployment with a horizontal pod autoscaler. Stretch: a multi-region read replica, rate limiting per client, a cost model in dollars per million redirects.

**Architecture.** Requests reach an ingress and a stateless API tier. Redirects read through Redis and fall back to the shard that owns the code; creates write to that shard. Click events go to a queue and a worker batches them into counters, so the redirect path never waits on a write. Prometheus scrapes every component, and the autoscaler scales the API tier on request rate or CPU.

```
k6 ─▶ ingress ─▶ API pods ─▶ Redis ─(miss)─▶ shard router ─▶ Postgres ×N
                    │
                    └─▶ queue ─▶ click worker ─▶ counters
Prometheus ◀── all ──▶ Grafana, HPA
```

**Stack.** Go or Python (FastAPI), Postgres, Redis, Redis Streams or NATS for the queue, k6 for load, Docker, kind or k3s locally and one small managed cluster, Helm or plain manifests, Prometheus and Grafana.

**Milestones.** Baseline service with a load test and its saturation point (8 h) · Read-through cache with hit-rate and latency numbers (6 h) · Asynchronous writes through a queue (7 h) · Sharded storage with a key-hash router (8 h) · Kubernetes deployment with autoscaling from manifests or Helm (6 h) · Case study with architecture diagrams at each stage (5 h). Total 40 h.

**Done when.** The baseline's saturation point is stated as the request rate where p99 latency crosses 100 ms or errors exceed 1 %. Each step has before and after numbers from the same k6 script on the same hardware. The final system sustains at least 5× the baseline's saturation rate within the same p99 target. Under a ramp from 10 % to 100 % of that load the autoscaler grows the API tier from 2 to at least 6 pods and back down within 10 minutes of the load ending. Everything deploys from the repository with one command.

**Measure and report.** Requests per second at saturation for each stage; p50, p95 and p99 latency for redirects and creates; cache hit rate against cache size; queue lag under peak load; pod count and latency over time during the autoscaling ramp.

**Pitfalls.** Running the load generator on the machine under test, so you measure k6. Uniform keys, which make any cache look useless or perfect; use a skewed distribution and say which. A database connection pool smaller than the pod count times the per-pod pool, which turns scaling out into errors. Autoscaling on CPU when the bottleneck is the database. Short-code generation that collides once writes are spread across shards.

**References.** system-design-primer, bytebytego, ddia, kubernetes-tutorials, prometheus-docs, google-sre-book, m-k8s-service.

**Write-up.** The case study: one architecture diagram per stage with its numbers, a saturation chart that layers all stages, the autoscaling timeline, and a final section on the next bottleneck and what it would cost to remove.
