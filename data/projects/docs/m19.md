# Build your own Redis in Rust

**Goal.** A Redis-compatible server in Rust that speaks RESP, serves strings, lists, hashes and sets to redis-cli and redis-benchmark, expires keys, persists with an append-only file or RDB snapshots, and is benchmarked against real Redis.

**Why.** A small but real network server: protocol parsing, an async event loop, data structures under concurrency, and durability. It builds Rust, async I/O and protocol design, and the nodes `software-architect/nosql-databases` and `software-architect/client-server`.

**Scope.** MVP: RESP2 parsing and encoding with pipelining; PING, ECHO, GET, SET (with EX, PX and NX), DEL, EXISTS, INCR, EXPIRE and TTL; LPUSH, RPUSH, LPOP, RPOP and LRANGE; HSET, HGET and HGETALL; SADD, SREM, SMEMBERS and SISMEMBER; lazy and active expiry; an AOF with `everysec` fsync replayed at start-up (or RDB snapshots). Stretch: RESP3, pub/sub, a replica, AOF rewriting.

**Architecture.** A Tokio listener accepts connections and spawns a task per client. Each task reads into a buffer, parses complete RESP frames, dispatches commands to the keyspace and writes the replies. The keyspace is a sharded map behind locks (or one task that owns the data and receives commands over a channel). An expiry task samples keys that have a TTL. Mutating commands go to the AOF writer, which fsyncs once a second.

```
redis-cli ─▶ TCP ─▶ conn task: buffer ─▶ RESP parser ─▶ dispatch
                                                        │
                    keyspace (sharded map) ◀────────────┤
                    expiry sampler ─▶ keyspace          └─▶ AOF writer ─▶ fsync
```

**Stack.** Rust stable, Tokio, the bytes crate, a hand-written RESP parser, redis-cli and redis-benchmark from Redis 7, cargo test, criterion for micro-benchmarks.

**Milestones.** RESP parser and encoder with tests (6 h) · Tokio server, PING, GET, SET and pipelining (6 h) · lists, hashes and sets (7 h) · lazy and active expiry (5 h) · AOF or RDB persistence with crash recovery (6 h) · redis-benchmark comparison and write-up (5 h). Total 35 h.

**Done when.** redis-cli works interactively for every MVP command, and `redis-benchmark -t set,get,lpush,lpop,sadd,hset -n 100000` completes without errors. Keys with a TTL are gone within 100 ms of expiring. After `kill -9` and a restart, every acknowledged write older than one second is present. Throughput is measured against Redis 7 on the same machine with the same flags and the same persistence setting.

**Measure and report.** Requests per second for each benchmarked command at 50 clients, with and without `-P 16` pipelining, against real Redis; p50 and p99 latency; memory per million keys against Redis; start-up replay time for an AOF of 1 million writes.

**Pitfalls.** Assuming one read is one frame; TCP splits and joins them. Holding a mutex across an `.await`. Active expiry that scans every key and stalls the server. Fsync on every write, or comparing against Redis with persistence on while yours has it off. Unbounded buffers for a client that sends faster than you reply.

**References.** build-your-own-x, rust-book, crust-of-rust, zero2prod, ddia, w-sys-tcp-echo.

**Write-up.** The command table, the throughput chart against Redis, a diagram of a connection task, the crash test, and where your server spends its time compared with Redis.
