# Pong or Breakout in C with raylib, fixed timestep

**Goal.** A complete Pong or Breakout in C on raylib, with score, lives, sound and a pause screen, a fixed-timestep loop, a warning-free build and a clean sanitizer run.

**Why.** Your first C program that is not an exercise, sized to finish in a few weekends. It builds C, raylib and Makefiles, and the nodes `game-developer/c-cpp`, `game-developer/collision-detection`, `game-developer/aabb` and `game-developer/linear-velocity`. The fixed-timestep loop is the same one every later simulation uses.

**Scope.** MVP: one game with title and pause screens, score and lives, three sound effects, a simple computer opponent (Pong) or a brick layout loaded from a text file (Breakout), keyboard input, and a Makefile or CMake build for Linux and one other platform. Stretch: a WebAssembly build with emscripten, particles, ball-speed ramps, gamepad input.

**Architecture.** The main loop accumulates real elapsed time and steps the simulation in fixed 1/120 s ticks, then renders once, interpolating between the last two states. Game state lives in one plain struct; update functions take it by pointer; rendering only reads it. Collisions are swept circle-against-box tests for paddles, walls and bricks.

```
frame: dt ─▶ accumulator ─▶ while (acc ≥ h) update(&state, h) ─▶ render(lerp)
                                  │
                       input, collisions, score, audio events
```

**Stack.** C99, raylib 5, GCC or Clang with `-Wall -Wextra -Werror`, Make or CMake, AddressSanitizer and UndefinedBehaviorSanitizer, Valgrind on Linux.

**Milestones.** Window, input and the fixed-timestep loop (3 h) · ball, paddles, collisions and scoring (6 h) · lives, game states, menus and pause (4 h) · sound and polish (3 h) · clean-machine build, sanitizer runs and README (4 h). Total 20 h.

**Done when.** A fresh clone builds with one command on a clean machine with no warnings under `-Wall -Wextra`. A full game played under ASan and UBSan reports no leaks and no undefined behaviour. With the frame rate capped at 30, 60 and 144 FPS and uncapped, a recorded 60-second input replay ends with the identical ball position and score, which proves the simulation does not depend on frame rate.

**Measure and report.** Final ball position and score after the replay at each frame-rate cap (bit-identical); frame time p50 and p99; binary size; lines of code; sanitizer output.

**Pitfalls.** Tunnelling: a fast ball passing through a paddle in one step. The spiral of death when an update takes longer than the step; clamp the accumulator. Replay drift because input is sampled per frame instead of per tick. Sounds or textures loaded every frame. Testing only on your own machine, then finding a missing library path on another.

**References.** raylib, beej-c, modern-c, gaffer-on-games, w-sim-fixed-timestep, handmade-hero.

**Write-up.** A gameplay GIF, the build command, a diagram of the loop, the replay results at four frame rates, and what you would change for the year 1 capstone.
