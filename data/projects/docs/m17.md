# Buffer pool and B+tree (CMU 15-445 labs)

**Goal.** BusTub's buffer pool manager with its replacement policy, and a concurrent B+tree index with insert, delete, iterators and latch crabbing, passing the course's local tests, plus a benchmark of your own and a short design note.

**Why.** These are the two structures at the bottom of every relational database. It builds C++, concurrency and storage engines, and the node `software-architect/sql-databases` from the inside. It also trains you to work inside a large existing codebase.

**Scope.** MVP: the buffer pool project (LRU-K replacer, disk scheduler, buffer pool manager with page guards, as in recent offerings) and the B+tree project (search, insert with splits, delete with merge and redistribution, an iterator, latch crabbing with an optimistic descent), both from the semester you follow; the local tests including the concurrent ones; a benchmark harness; the design note. Stretch: the leaderboard tasks, a comparison with SQLite's B-tree page layout.

**Architecture.** The buffer pool maps page ids to frames through a page table; the replacer picks an evictable frame by backward k-distance; dirty pages go to disk through the disk scheduler's background thread. Page guards pin and latch a page for their lifetime. The B+tree keeps internal and leaf pages in buffer-pool frames; each operation descends from the root taking latches, and releases the ancestors once a child is safe.

```
B+tree op ─▶ page guard ─▶ buffer pool ─▶ page table ─▶ frame
                               │ miss               ▲
                        replacer (LRU-K) ─▶ evict ──┘
                               │
                    disk scheduler ─▶ disk manager ─▶ db file
```

**Stack.** C++17, BusTub, CMake, GoogleTest, the course's clang-format and clang-tidy checks, ThreadSanitizer and AddressSanitizer, perf.

**Milestones.** LRU-K replacer and disk scheduler (7 h) · buffer pool manager and page guards (8 h) · B+tree search, insert and splits (9 h) · delete with merge and redistribution, and iterators (8 h) · latch crabbing and concurrent tests (5 h) · benchmark and design note (3 h). Total 40 h.

**Done when.** Every local test for both projects passes, including the concurrent ones, under ThreadSanitizer with no reports. Your own benchmark runs mixed inserts, lookups and deletes over 1 million keys from 1, 4 and 8 threads with buffer pools of 64 and 1 024 frames, and checks the tree against a `std::map` at the end. The design note explains the replacer, the page guards and the crabbing protocol; the solution code stays private as the course asks.

**Measure and report.** Operations per second by thread count and pool size; buffer-pool hit rate; tree height and leaf fill factor after 1 million random inserts; time spent waiting on latches, from a profile.

**Pitfalls.** Pin counts that never return to zero, so the pool fills and every fetch fails. Deadlock from taking latches in different orders, or holding a page latch while waiting for the buffer-pool latch. Releasing a parent too early on delete, when a merge can propagate upward. Off-by-one at the split point. Pushing the solution to a public repository.

**References.** cmu-15-445, ddia, effective-modern-cpp, cpp-core-guidelines.

**Write-up.** Diagrams of the buffer pool and of one B+tree split, the throughput chart, the benchmark's correctness check, and the concurrency bug that took longest, all without solution code.
