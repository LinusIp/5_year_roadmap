# Sharded, linearisable key-value store

**Goal.** A fault-tolerant, linearisable key-value service on your own Raft, then sharded across replica groups with shards migrating during live reconfiguration, passing the MIT 6.5840 lab 4 and 5 tests, with a design note on exactly-once semantics.

**Why.** Software Architect roadmap: `software-architect/distributed-systems` and `software-architect/acid-cap-theorem`. Skills: linearizability, sharding and reconfiguration. It is the layer where consensus becomes a service: duplicate detection, snapshots of application state, and moving data between groups without losing or double-applying a write.

**Scope.** MVP: the replicated key-value server with client retries and duplicate detection, snapshots when the Raft state grows, the shard controller, and the sharded store with migration and garbage collection of moved shards as the labs require. Stretch: serving reads for shards that are not moving during a reconfiguration; a linearizability check with Porcupine on your own workload. As in project 37, solutions stay in a private repository and the design note is public.

**Architecture.** Clients send Get, Put and Append to the leader of the group that owns the key's shard. Each server submits the operation to Raft, waits for it on the apply channel, and applies it to the state machine, which keeps the last request id per client to drop duplicates. The shard controller is itself a replicated service holding numbered configurations. Groups poll it, process configurations in order, and pull shard data and duplicate tables from the previous owner through Raft before serving those shards.

```
client ─▶ group leader ─▶ Raft log ─▶ apply ─▶ state machine (kv + dedup)
                                                     ▲
shard controller ─▶ config N ─▶ groups pull shards ──┘
```

**Stack.** Go, your Raft from project 37, the 6.5840 lab skeletons and test suites, the race detector, and the parallel test script.

**Milestones.** Replicated key-value server on Raft with duplicate detection (10 h) · Snapshots of the key-value state (6 h) · Shard controller with balanced, minimal-move rebalancing (6 h) · Sharded store with migration during reconfiguration (14 h) · Exactly-once design note and the 100-run test loop (4 h). Total 40 h.

**Done when.** Every lab 4 and lab 5 test passes 100 consecutive times with the race detector on. Snapshots keep the persisted Raft state under the limit the tests set. The shard controller's rebalancing moves the minimum number of shards on join and leave, checked by its tests. The design note explains, with a sequence diagram, how a retried Append is applied exactly once even when it crosses a leader change and a shard migration.

**Measure and report.** Operations per second and median latency for the unsharded store under the test harness; time to complete a reconfiguration as a function of shard size; failures per 1,000 runs per test before and after the last fixes; persisted state size with and without snapshots.

**Pitfalls.** Answering a client from a leader that has lost leadership, which breaks linearizability; wait for the entry at the index you submitted and check its term. Duplicate tables that are not part of the snapshot or the shard transfer, so retries apply twice after a restart or a move. Applying configurations out of order or skipping one. Deleting a shard's data before the new owner confirms it has it.

**References.** mit-6-5840, paper-raft, kleppmann-distributed-systems, ddia, paper-spanner, m24.

**Write-up.** The public design note on exactly-once semantics, a diagram of a reconfiguration from config N to N+1, the throughput and reconfiguration-time table, and a list of the bugs found and the invariant each one broke.
