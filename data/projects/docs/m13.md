# Path tracer with a BVH

**Goal.** A multithreaded C++ path tracer that renders triangle meshes of 100k triangles or more through a bounding volume hierarchy, with importance sampling and a Cornell box that converges.

**Why.** Game Developer roadmap: `game-developer/ray-tracing`, `game-developer/bvh`, `game-developer/sampling`, `game-developer/rendering-equation`, `game-developer/diffuse` and `game-developer/specular`. Skills: Monte Carlo integration (every pixel is an estimator, and you will see its variance), acceleration structures, and multithreading. It turns the Ray Tracing in One Weekend renderer from a sphere demo into something that can render real assets, and the BVH reappears in the physics engines and the Vulkan ray-tracing project.

**Scope.** MVP: triangles and an OBJ loader, a BVH built with the surface area heuristic, diffuse, metal, dielectric and emissive materials, cosine-weighted hemisphere sampling, next-event estimation for area lights, tiled rendering on all cores, PNG and EXR output. Stretch: a microfacet GGX material, multiple importance sampling, a flattened BVH with SIMD traversal, a progressive preview window.

**Architecture.** A scene loader turns OBJ files and a scene description into triangles and materials. The BVH builder sorts primitives into a tree, then flattens it into an array for traversal. A tile scheduler hands 32×32 tiles to worker threads. Each worker traces camera rays, intersects them with the BVH, samples a material and a light at each bounce, and accumulates radiance into a float framebuffer, which is tone mapped and written out.

```
scene ─▶ loader ─▶ BVH builder ─▶ flat BVH
                                     │
tile queue ─▶ workers ─▶ trace ◀─────┘
                 │
                 ▼
          framebuffer ─▶ tone map ─▶ PNG/EXR
```

**Stack.** C++20, CMake, `std::thread` or a small thread pool, tinyobjloader, stb_image_write and tinyexr, and the Stanford dragon or a similar 100k+ triangle mesh.

**Milestones.** Port the In One Weekend core to triangles with an OBJ loader (6 h) · BVH with surface-area splits and a brute-force comparison (8 h) · Materials, emissive lights and a Cornell box (7 h) · Importance sampling: cosine hemisphere and next-event estimation (6 h) · Multithreaded tiles with render timing (4 h) · Benchmarks and write-up (4 h). Total 35 h.

**Done when.** On a mesh of at least 100k triangles, the BVH renders at least 100× faster than brute force at the same image and sample count, both timed by a benchmark target in the repository. The Cornell box converges: root-mean-square error against a 16,384-sample reference roughly halves each time the sample count quadruples, from 16 to 1,024 samples per pixel. Next-event estimation reaches the same error as plain path tracing with at least 4× fewer samples. Rendering scales at least 6× from one thread to eight.

**Measure and report.** Rays per second with and without the BVH; BVH build time and node count; error against samples per pixel on a log-log plot for plain sampling, cosine sampling and next-event estimation; render time against thread count; time to render the Cornell box at 1,024 samples per pixel at 512×512.

**Pitfalls.** Shadow acne from intersecting the surface you just left; offset the origin or use a minimum distance. Dividing by a probability density that does not match how you sampled, which biases the image without crashing. Midpoint splits instead of the surface area heuristic, which leaves long thin nodes and a disappointing speed-up. Threads writing to shared counters or one random generator, which serialises everything; give each thread its own. Judging convergence by eye instead of against a reference.

**References.** rtiow, pbr-book, scratchapixel, cmu-15-462, paper-microfacet, m12.

**Write-up.** A gallery with the Cornell box and the dragon, the speed-up table for the BVH, the convergence plot, the thread-scaling chart, and a paragraph on what moving traversal to the GPU would take.
