# Vulkan model viewer, then a compute particle system (one million particles)

**Goal.** A Vulkan application that loads a textured glTF model with an orbit camera, then adds a compute-shader particle system that keeps one million particles above 60 frames a second, with the frame cost of each part measured.

**Why.** Game Developer roadmap: `game-developer/vulkan`, `game-developer/spir-v`, `game-developer/glsl` and `game-developer/graphics-pipeline`. Skills: Vulkan, GPU synchronisation and memory management. Vulkan makes explicit what OpenGL hid: queues, barriers, descriptor sets and memory types. The compute half is the template for the GPU fluid, the cloth solver and the capstone engine's physics.

**Scope.** MVP: instance, device and swapchain with validation layers, resize handling, depth buffer, glTF loading with textures and mipmaps, an orbit camera, two frames in flight, a compute pass that integrates particles in a storage buffer and a graphics pass that draws them as points. Stretch: indirect drawing, particle sorting for alpha blending, a curl-noise force field, GPU timestamps shown in an overlay.

**Architecture.** A device layer owns the instance, the queues and a memory allocator. The renderer records each frame's command buffer: a compute dispatch that updates particle positions and velocities, a pipeline barrier from shader write to vertex read, then the render pass that draws the model and the particles. Per-frame resources (uniforms, command buffers, semaphores and fences) are duplicated for each frame in flight.

```
glTF ─▶ loader ─▶ vertex/index buffers, textures
                                  │
particles (SSBO) ─▶ compute ─▶ barrier ─▶ render pass ─▶ swapchain
         ▲                                     │
         └────────── next frame ◀──────────────┘
```

**Stack.** C++20, Vulkan 1.3 with dynamic rendering, vk-bootstrap, Vulkan Memory Allocator, GLFW, cgltf, GLSL compiled to SPIR-V with glslc, RenderDoc and the validation layers.

**Milestones.** Triangle with validation layers, swapchain and resize (8 h) · Model viewer: glTF, textures, depth and camera (10 h) · Compute particle system with storage buffers and barriers (10 h) · Scale to one million particles and tune (5 h) · GPU timestamps, frame-time numbers, video and README (7 h). Total 40 h.

**Done when.** The viewer loads a glTF model with textures, resizes without errors, and runs with the validation layers clean, synchronisation validation included. One million particles run above 60 frames a second at 1080p on your GPU while the model is drawn. Frame time with and without the particle pass is in the README, measured with GPU timestamp queries over 1,000 frames. The repository is public and the README links a short video.

**Measure and report.** Frame time at p50 and p99 for the viewer alone and with 100k, 1M and 4M particles; compute and draw time per pass from timestamps; the particle buffer's memory and bandwidth per frame; the effect of workgroup size (64, 128, 256) on compute time.

**Pitfalls.** Missing or over-broad barriers between the compute write and the vertex read: the first gives flicker, the second stalls the GPU. One set of per-frame resources shared by two frames in flight. Forgetting to recreate the swapchain and depth image on resize. Storage-buffer layout mismatches between C++ and GLSL (std430 padding of vec3). Reading frame time from the CPU while the GPU is the bottleneck.

**References.** vulkan-tutorial, vkguide, khronos-vulkan-tutorial, khronos-vulkan-samples, rtr4, m18.

**Write-up.** A short video of the model and the particles, the frame-time table across particle counts, a diagram of the frame's synchronisation, and a note on what a GPU-driven renderer would change.
