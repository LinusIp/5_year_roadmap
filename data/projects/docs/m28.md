# Event pipeline with Kafka, stream processing and an observability stack

**Goal.** An event pipeline that takes events from producers through a partitioned Kafka topic and a windowed stream processor into a sink, produces each aggregate effectively once even when a consumer is killed, and is watched by metrics, logs, traces and a lag alert.

**Why.** Software Architect roadmap: `software-architect/messaging-queues`, `software-architect/cqrs-eventual-consistency` and `software-architect/distributed-systems`. Skills: Kafka, stream processing (event time, watermarks, late data) and observability. It is the data path behind every metrics dashboard you will build later, including the telemetry from the year 4 sensor node.

**Scope.** MVP: two producers emitting events with event-time timestamps and some out-of-order and late events, a topic with six partitions, a consumer group running a tumbling and a sliding window aggregation with a grace period for late events, a Postgres sink, transactional or idempotent output, Prometheus, Grafana and OpenTelemetry traces, one consumer-lag alert. Stretch: a schema registry with a compatible schema change, a dead-letter topic, replay of a day of events into a fresh sink.

**Architecture.** Producers send keyed events to the input topic. The processor consumes as a group, assigns events to windows by event time, holds windows open until the watermark passes plus the grace period, and emits aggregates. Output is written either in a Kafka transaction together with the consumer offsets, or as upserts keyed by window and key so a replay overwrites rather than duplicates. Every component exports metrics and spans to an OpenTelemetry collector.

```
producers ─▶ topic (6 partitions) ─▶ processor group ─▶ aggregates ─▶ sink (upsert)
                                          │
                   OTel collector ◀── metrics, logs, traces ──▶ Prometheus ─▶ Grafana ─▶ alert
```

**Stack.** Kafka in KRaft mode under Docker Compose, Kafka Streams (Java or Kotlin) or Flink, or Python with confluent-kafka for a hand-rolled processor, Postgres, Prometheus, Grafana, the OpenTelemetry collector and Jaeger or Tempo, kafka-exporter for lag.

**Milestones.** Kafka cluster, topic design and producers with event-time data (6 h) · Windowed aggregation with watermarks and late-event handling (10 h) · Effectively-once sink and the kill-a-consumer test (8 h) · Metrics, logs, traces and the lag alert (10 h) · Load test, results and write-up (6 h). Total 40 h.

**Done when.** A test script sends a known set of 1,000,000 events, kills a consumer mid-run, restarts it, and checks that every window's count and sum in the sink match the expected values exactly: no gaps, no duplicates. Events up to the grace period late are counted in their window; later ones are counted in a late-events metric. The lag alert fires within two minutes of stopping the consumers and clears after they catch up. One trace follows an event from producer to sink.

**Measure and report.** Throughput in events per second against partition count (1, 3, 6, 12); end-to-end latency from event time to sink at p50 and p99; consumer lag during and after the kill test; late events dropped against grace period; time for a rebalance to complete.

**Pitfalls.** Windows keyed by processing time instead of event time, so a restart reshuffles results. Committing offsets before the output is durable, which loses data, or after without idempotence, which duplicates it. A single hot key that pins one partition. Consumer rebalances that stall processing because the poll loop blocks too long. Metrics with a label per key, which takes down Prometheus.
